# 本机首次接入：账号、官方验证、选车

运行 `uv run lixiang-setup`，普通表单只填写本人手机号和密码。应用配置已经内置，设备身份由本机生成并保存；不需要手工填写 client_id、audience、scope、User-Agent、版本或 VIN。向导仅监听 `127.0.0.1:8765`，独立于 MCP，账号输入不会经过模型或 MCPHub。

**目前仍有明确的签名材料障碍。** 指定上游可以用手机号/密码建立账号会话，但没有实现从该会话生成个人车辆 API 签名密钥。账号登录成功后，若缺少本人合法持有、相互匹配的签名材料，向导会停在“签名材料尚未就绪”，不会读取或伪造车辆，也不会复制上游作者设备的默认秘密。源码证据见下文。完整流程已通过合成 HTTP、真实本地浏览器和 MCP 验证，尚未使用真实账号或车辆。

## 1. 在自己的电脑启动

从 [开发分支](https://github.com/skyjt/lixiang-mcp/tree/feat/standalone-mcp-v1) 拉取并 `uv sync --frozen` 后：

```bash
uv run lixiang-setup
```

浏览器会打开本地向导；如果没有自动打开，用**本机浏览器**打开终端显示的私密 `secrets/onboarding/launch.html` 文件。该文件含本次启动的本地访问能力，不要发送给别人。重启向导后重新打开该文件，旧页面授权失效。无桌面时使用 `uv run lixiang-setup --no-browser`，再本人在同一电脑打开文件；首版不支持把向导放到 NAS 公网或通过网关使用。

可用 `--state-dir` 选择自己的私密目录，或 `--port` 更换本机端口。不要同时启动两个使用同一目录的向导；单进程锁会拒绝。更换目录会建立另一套本地身份，不是清除登录限制或复制现有车辆实例的方法。

输入密码仅使用页面的密码框，别把密码/token 放进命令参数、shell 历史、环境变量、聊天、issue 或 PR。默认位置已被 Git 和 Docker 构建上下文忽略。

## 2. 账号登录与官方 H5 验证

1. 填写本人手机号和密码，点击“登录并继续”。本机会生成或复用该账号的设备身份，先保存进度，再尝试登录。
2. 如果服务器要求额外验证，页面显示指向 `https://account.lixiang.com/app-auth` 的官方链接。链接使用同一设备 ID；不含手机号、密码、验证码或 token。
3. 在官方网页完成滑块/短信等验证，然后回本地页面点击“我已完成官方验证，继续”。验证码只交给理想官网；本向导没有验证码输入框，也不接收官网回调 cookie。
4. “继续”只允许一次受限登录尝试，不能自行把设备标为受信任。仍须真实密码/PAKE、redirect/state 和 token 校验通过。没有后台反复试密码，也没有绕过官网验证的实现。

每账号 15 分钟内最多发起 3 次向导尝试，每次最多一次密码登录；重复点击由进度版本校验拒绝，不会追加尝试。状态轮询只读本机进度，不轮询理想账号。次数跨重启保存；达到上限后等待冷却，由本人明确重试。签名导入后启动的检查也计入这个保守上限。

首次操作会访问理想登录端点、登记设备；只读车辆权限并不代表完全没有账号侧影响。上游提示 PAKE 登录可能影响官方 App 会话，这一点尚未实测。遇到错误密码、未知挑战、异常跳转或连接错误时停止盲试，页面只显示固定错误码。

## 3. 签名材料缺失或设备不一致

密码登录 token 与 x-chj API 签名密钥是两类材料，不能互换。当前支持本人在本机显式导入 JSON；模板是根目录的 `signing-material.example.json`，需通过安全渠道自行准备，不能直接运行占位值：

| 字段 | 含义 |
| --- | --- |
| `device_id` | 这套签名材料对应的本人设备标识，即上游所称 xdev / X-CHJ-Deviceid |
| `key_id` | 对应签名 key 的标识 |
| `hac_key_hex` | 本人原始 32 字节 HMAC key 的 64 位 hex 表示 |
| `app_token` | 对应应用/设备 token；不是主登录 access token，也不是 MCPHub token |

本项目不实现这些材料的自动提取/生成，不扫描既有 HA、浏览器或 App 文件，也没有凭空创建新签名密钥的接口。没有材料就停在此步骤，继续用 mock 开发。不要借用作者或他人的设备材料。

如果材料中的设备与刚才的本机登录设备不同，向导要求明确点击“使用此签名设备重新验证”。它会丢弃旧账号会话，更新本机设备身份，再用这个设备重新走登录/必要的官方 H5 验证。后续密码登录、scope 交换、SSO cookie 和 API 签名使用同一个设备值。这保证本项目内部一致，**不能证明该套材料与当前理想服务器兼容**；不得跳过该检查混用两个设备。

## 4. 选择车辆并生成只读连接

具备账号会话和配套签名材料后，向导读取 SAOS 车辆列表，只展示当前账号获准且状态可用的车辆。页面显示车辆名称和 VIN 尾号供本人区分，不自动选择第一辆。选中需要接入的车辆并保存。

向导自动生成私密运行目录，并显示其中 `server.json` 的绝对路径。以下命令中的路径替换成**自己页面显示的路径**，路径本身不含密码/token：

```bash
LIXIANG_CONFIG=/你的私密目录/export-对应目录/server.json uv run lixiang-mcp
```

此时本机 MCP 为 `http://127.0.0.1:8001/mcp`。同目录 `backend-token` 是客户端专用凭据，应让可信本地客户端从文件或安全凭据存储读取，避免在终端打印或写入命令历史。`backend-auth.json` 只授予所选车辆的 `vehicle:read`；`enable_control`、`allow_real_control`、空调能力和位置能力都保持 false。

只读验收按顺序调用 `list_vehicles`、`get_vehicle_capabilities`、`get_connection_status`、`get_vehicle_state`、`get_charging_status`，对照本人官方 App 检查时间、单位及陈旧标记。缺失信号保持 unknown/stale；`model_known` 只表示云端 modelId 与所选记录绑定一致，不等于已验证车型能力。没有完整车型能力数据库，向导不会开启任何控制。

可以运行 `uv run python scripts/readonly_client.py --config /你的私密目录/export-对应目录/server.json` 完成上述只读调用；它从同目录私密文件读取后端凭据，仅输出信号数和陈旧数。`scripts/smoke_client.py` 固定检查 mock 的三辆车，不适用于这个真实配置。先在 mock 完成 SDK 联调，不需要先接 MCPHub。

## 5. 中断、取消、重启与失效恢复

- 页面重复点击不会重复执行；进度版本变化后旧请求被拒绝。
- 取消首次接入会取消后台任务，并从当前检查点移除账号密码、签名和会话；保留设备身份与尝试次数。不是对文件系统备份/旧磁盘块的安全擦除保证。
- Ctrl-C、断电或进程退出后，下次恢复显示中断状态；只有本人继续才重新联网。官网验证尚未完成时仍使用原设备。
- 完成连接后重新登录，先停止 MCP 服务，再运行同一目录的向导，输入同一账号的最新密码。取消重新登录会恢复已提交的账号、会话及完整车辆选择，不删除数据库或重新生成幂等历史。云端列表暂时缺少某辆车时不会换绑；车辆恢复后仍使用已导出配置中的原 vehicle_id。
- 已存在连接锁定账号和所选车辆集合。更改选择/账号需要另行审阅迁移，不能靠重新导出绕过数据库绑定。首次可以同时选择多辆车；不同账号使用独立私密目录和独立服务，不把同一实车重复绑定到多个可控实例。
- 向导导出的本机配置开启 `persist_vehicle_sessions`：账号 cookie、主/refresh token 的轮换会写回私密协议文件；启动时验证账号、设备及 profile 一致后恢复。文件不可写或运行中配置被修改会固定报错并停止该账号继续使用，不忽略持久化失败。取消请求仍会等待已开始的落盘结束，再释放写锁；重复取消也不能让旧会话覆盖新会话，落盘失败优先报告并阻断账号。
- 后端发现验证码/风控/凭据失效时不会调用本机浏览器或让 MCP 模型接管登录。由本人停止 MCP、打开向导处理。只读模式的“续期失败”不代表车辆已离线。

向导检查点 `state.box` 使用随机密钥的 SecretBox 加密，密钥保存在同一私密目录的 `key.bin`；文件 0600、目录 0700、拒绝符号链接、原子替换并 fsync。导出给运行服务的 `vehicle-protocol.json` 则是 0600 的私密 JSON，含服务所需材料，不能公开。这里没有 OS Keychain/HSM，也不防同 UID 或 root 读取；备份需要保护整个私密目录，不能只复制检查点再丢失密钥。

Docker 的只读 file secret 挂载不能写回轮换材料。默认 mock Compose 不受影响；以后迁移真实配置时需选择受保护可写目录，或显式关闭 `persist_vehicle_sessions` 并接受重启可能重新登录。首次接入仍建议在本人电脑完成，不能把 setup 端口代理到公网。

## 源码证据和剩余障碍

基线为 `ha-lixiang v1.3.2 / 7e9726bb7f78c5de376c88b271ac08fac8e2b997`：

- `config_flow.py:58–77` 普通表单为手机号和密码；`198–237` 复用/保存身份，但仍保留 DEFAULT_DEVICE_ID 兜底。本项目只生成本人新身份或复用本人已保存身份。
- `config_flow.py:482–547` 当前页面直接给官网 H5 URL；`auth_web.py` 的辅助页面仍存在，但不是必须部署的前提。此前文档将“没有服务端验证码完成协议”写成“不能实现官方网页辅助”过度收窄，已纠正。
- `config_flow.py:555–602` 完成登录时补齐默认签名材料，缺失则中止；`pake_login.py` token 响应不生成 hac_key/key_id。`const.py` 的 `EP_KEY_SUITE` 只有端点常量，指定版本没有它的个人签名材料初始化实现，本项目不猜请求格式或实测探测。
- `li_api.py:345–405` 密码登录优先 xdev，而 scope exchange 使用另一个 device_id。本项目不复制这个不一致：材料换设备必须重新验证，统一 cookie/登录/scope/signing 的设备。
- 非秘密应用参数来自 `pake_login.py:49–57` 与 `li_api.py:49–63,113–115,453–480`，内置于 `cloud/profiles.py` 并带固定 profile_id；没有 DEFAULT_HAC_KEY、DEFAULT_XDEV、DEFAULT_APP_TOKEN 或其他设备身份。

剩余实质障碍是本人签名材料的合法来源与实际兼容性，以及官方 H5 验证后的设备信任行为、真实账号/车型/信号语义和网关/NAS 实测。测试证明本地流程、请求形状、授权隔离及失败策略，没有证明理想当前服务器或真实车辆接受该流程。
